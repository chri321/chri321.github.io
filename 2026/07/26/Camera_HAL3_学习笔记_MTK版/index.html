Camera HAL3 学习笔记（MTK 平台版）

2026-07-26

基于 Android Camera HAL3 接口整理，面向 HAL 开发初学者。Vendor HAL 实现以联发科（MTK）MtkCam3 为例。

一、HAL3 是什么

HAL3（Hardware Abstraction Layer 3）是 Android Framework 与相机硬件之间的标准接口层。

  • HAL1（Android 5.0 之前）：同步命令式接口，已被废弃
  • HAL3（Android 5.0+）：异步 Pipeline 接口，当前标准

HAL3 定义了 Framework 和 Vendor HAL 之间的通信契约：Framework 怎么发请求、HAL 怎么回结果、Buffer 怎么流转，全部标准化。

二、架构分层

层级核心组件职责
应用层Camera2 APIApp 调用 capture()、接收 onCaptureCompleted()
FrameworkCamera3DeviceStream 生命周期、Request 队列、Result 分发、Buffer 管理

硬件层Sensor + ISP + Driver曝光、模数转换、图像处理

三、四大核心接口

3.1 configureStreams()

作用：在 Session 创建时，Framework 与 HAL 协商所有输出流的配置。

HAL 需要：

  • 检查请求的 Stream 组合是否支持
  • 回填每个 Stream 的 usage（Gralloc 使用标志）和 max_buffers（最大 Buffer 数）
  • 内部重配置 ISP Pipeline（重量级操作，通常几百毫秒）

约束：调用后所有之前的 Request 状态清空。中途新增 Stream 必须先 stop、reconfigure、再 start。

3.2 processCaptureRequest()

作用：Framework 向 HAL 下发一帧捕获请求。

关键设计：

  • 非阻塞：必须立即返回，不能等待图像采集完成
  • frame_number：严格单调递增，用于 Request/Result 匹配
  • settings：camera_metadata_t 结构，携带曝光、对焦、白平衡等参数
  • output_buffers：本次请求要填充的 Buffer 数组

3.3 processCaptureResult()

作用：HAL 向 Framework 回调处理结果。

关键设计：

  • frame_number 必须与对应 Request 一致
  • partial_result：支持分阶段返回结果
    • partial_result = 1：先返回 3A 状态等早期 metadata
    • partial_result = partialResultCount：返回完整结果（含图像 Buffer）
  • output_buffers：已填充图像数据的 Buffer

3.4 notify()

作用：HAL 上报异步事件。

事件类型：

  • CAMERA3_MSG_SHUTTER：传感器开始曝光的精确时间戳（纳秒级），用于 EXIF、音视频同步、多摄对齐
  • CAMERA3_MSG_ERROR：Buffer 错误、Request 错误、硬件错误等

四、Request / Result 完整流转

步骤发起方操作说明
①Appcapture(CaptureRequest)用户触发拍照/预览
②Camera3DeviceprocessCaptureRequest()非阻塞下发给 HAL
③Camera3DevicedequeueBuffer()向 BufferQueue 申请空 Buffer
④BufferQueue返回句柄Buffer 所有权移交给 HAL
⑤Vendor HAL / ISP曝光 → 处理 → 写入Sensor 曝光，ISP 降噪/调色/锐化
⑥Vendor HALprocessCaptureResult() + notify(SHUTTER)回调结果，Buffer 所有权归还
⑦Camera3DeviceonCaptureCompleted()通知 App，匹配 frame_number
⑧Vendor HALqueueBuffer()图像入队，App 可消费

六、BufferQueue 与零拷贝

Buffer 流转依托 Android BufferQueue 生产者-消费者模型：

阶段操作说明
HAL 获取dequeueBuffer()从 BufferQueue 空闲池取出空 Buffer
HAL 写入ISP 处理 + release_fence图像数据写入，设置 fence 通知消费者
App 消费acquireLatestImage()从 BufferQueue 取走已填充 Buffer
App 释放releaseImage()消费完毕，Buffer 归还空闲池

Sync Fence 机制：

  • acquire_fence：HAL 必须等待此信号才能写入（防止 GPU/显示子系统还在使用）
  • release_fence：HAL 写入完成后设置，告知 Framework/App 数据已就绪
  • 配合 Gralloc 分配的共享内存，实现跨进程零拷贝

七、Stream 类型

类型数据方向典型场景
OUTPUTHAL → App预览（SurfaceView/TextureView）、拍照（ImageReader JPEG）、录像（MediaRecorder Surface）
INPUTApp → HALZSL Reprocessing（将缓存帧送回 HAL 做 HDR/降噪合成）
BIDIRECTIONAL双向原地处理（读一帧、处理、写回同一 Buffer），实际很少用

格式选择建议：

  • 预览：IMPLEMENTATION_DEFINED（让 HAL 自选最优格式，通常为 NV12）
  • 图像处理：YUV_420_888（明确指定，避免 HAL 软件转换）
  • 拍照：JPEG（节省内存）或 RAW_SENSOR（专业模式）

八、Pipeline 深度

Pipeline 深度 = 同一时刻 HAL 内部正在处理的 Request 数量。

  • 深度 = 1：串行处理，延迟最低（首帧延迟 ≈ 单帧处理时间），但帧率最低
  • 深度 = 4（典型值）：平衡延迟与吞吐，大多数手机的默认配置
  • 深度 = 8：吞吐最高，但首帧延迟 = 8 × 单帧处理时间

流量控制：

真实帧率 = min(传感器最大帧率, 1秒 / 单帧处理时间 × PipelineDepth)

九、In-Flight Request 追踪

Camera3Device 维护 InFlightMap，记录所有已提交给 HAL 但未收到完整 Result 的 Request：

  • HAL 多次返回 partial result 时，Camera3Device 合并进 collectedResult
  • 当 partial_result == partialResultCount 时，该 Request 视为处理完成

十、Android 15 演进：HIDL → AIDL

对比项HIDLAIDL（稳定版）
接口描述.hal 文件，Hidl-gen 生成.aidl 文件，Aidl-cpp/java 生成
版本管理不可变，改接口需新版本支持向后兼容的接口演进
性能独立 hwbinder与 binder 统一，减少开销
工具链HIDL 独立工具链统一 AIDL 工具链
Android 15逐步废弃推荐使用

HAL3.5 新增 Buffer Management API：

  • requestStreamBuffers()：HAL 主动向 Framework 请求 Buffer
  • returnStreamBuffers()：HAL 主动归还 Buffer
  • 优势：HAL 可更灵活管理内部 Buffer 池，减少不必要内存拷贝

十四、核心要点总结

  1. HAL3 是异步 Pipeline 协议：4 个接口定义了 Framework 与硬件的完整通信契约
  2. Request/Result 一一对应：frame_number 是匹配键，严格递增，不可乱序
  3. Stream 支持多流并发：预览、拍照、录像各走独立的 BufferQueue，零拷贝传递
  4. Metadata 结构化：所有参数/结果用 camera_metadata_t 传递，类型安全、可验证
  5. Buffer 复用 + Fence 同步：Gralloc 分配共享内存，sync fence 实现异步零拷贝
  6. Pipeline 深度权衡吞吐与延迟：深度越大帧率越高，但首帧延迟越大
  7. Android 15 迁移 AIDL：接口统一、向后兼容，新增 Buffer Management API
  8. MTK MtkCam3 架构：Middleware（对接 Framework）+ Pipeline（HWNode 图像处理），核心节点为 P1Node → P2CaptureNode/P2StreamingNode → JpegNode
